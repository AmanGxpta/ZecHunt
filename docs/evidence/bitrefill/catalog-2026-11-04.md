# Bitrefill India reward catalog — 4 Nov 2026

Source of truth in code: `lib/bitrefill/catalog.ts` (`REWARD_CATALOG`). It is the v2 adapter's hard allowlist and the v1 bridge's catalog.

## Method (read-only)

All calls went through the Bitrefill MCP endpoint with the configured key. The probe script was hard-wired to refuse any tool except `tools/list`, `search-products`, `get-product-details` and `get-invoice-by-id`. **No `buy-products` call was made.** No key, code or token was printed.

1. `search-products`: `query "*"`, `country IN`, `in_stock true`, `per_page 250`, once per category. The categories were `food`, `food-delivery`, `restaurants`, `groceries`, `retail`, `online-marketplaces`, `department-stores`, `apparel`, `electronics`, `games`, `game-stores`, `in-game-currencies`, `game-top-ups`, `entertainment` and `streaming`. There were also name searches for Amazon, Myntra, Nykaa and Zepto. That makes 19 search calls.
2. `get-product-details` (`currency USD`) for a 31-product shortlist (31 calls), plus 1 earlier call for the full shape of Swiggy.
3. `tools/list` once for the tool schemas.
4. `get-invoice-by-id` for the existing delivered invoice `3923a98e-e06e-4775-b8ea-d0db067a3683`: one shape call, one field-comparison call and one adapter round-trip (`getOrderStatus` + `getRedemption`), 4 calls in all. Only key names, lengths, character classes and booleans were printed.

Inclusion rules:
- `recipient_type: "none"` (code only)
- `in_stock: true`
- `country_code: IN`
- the package is **listed** with `package_currency: INR` and `payment_currency: USD`

Prices are what the balance pays, from `get-product-details` with `currency: USD`.

## Buyable under current caps

The current caps are **$0.55 per purchase, $0.55 daily, $0.55 total**. These caps were not changed.

- **Per-purchase cap only:** Swiggy Money ₹50, Subway ₹50 and AJIO ₹50 ($0.55 each) pass it.
- **Total cap:** the live v1 ledger (`.data/bitrefill.db`) already holds the first real purchase: 1 row, 55¢, invoiced. The bridge counts v1 spend, so **in the live database nothing is buyable until the total cap is raised.**

The per-purchase cap each tier needs before *every* product in it becomes buyable:

| Tier | Most expensive product | Per-purchase cap needed |
|---|---|---|
| ₹50 | Google Play ₹50 | **$0.57** |
| ₹100 | App Store & iTunes ₹100 | **$1.19** |
| ₹250 | Blinkit ₹250 | **$2.76** |
| ₹400 | Steam ₹325 | **$3.63** |

Daily and total caps must also cover however many purchases the founder wants per day or per campaign. For example, one ₹400-tier reward plus the $0.55 already spent needs a total cap of at least $4.18.

## Product-details reply shape (relevant fields)

```
{ id, name, country_code: "IN", currency: "INR", categories[], recipient_type: "none",
  in_stock: true,
  packages: [{ package_value: "50", package_currency: "INR", payment_price: "0.55", payment_currency: "USD" }],
  range?: { min, max, step, currency, note },     // custom denominations
  descriptions, instructions, termsConditions,    // provider HTML, untrusted
  ratings, reviews[] }                            // untrusted user text
```

`name`, `descriptions`, `instructions` and `reviews` are untrusted. The adapter never uses them as titles; titles come from the catalog's `brand`. `sanitizeProviderText` is available for showing any provider text as plain text.

## Real redemption shape (invoice 3923a98e-…)

`get-invoice-by-id` → `orders[0]`:
- **Keys:** `order_id`, `invoice_id`, `product{id,name,value,currency,url}`, `status: delivered`, `delivered_time`, `payment_method`, `refunded`, `access_link`, `is_esim_topup`, `is_archived`, `spent_history`, `redemption_available: true`, `redemption_info`.
- **`redemption_info`:** `{ pin: string(16, alphanumeric), other: "PIN Code: ######", expirationTime: ISO date, extraFields: { "PIN Code": string(6 digits) } }`.

The top level also carries `invoice_access_token` and `checkout_url`, and the order carries `access_link`. **All three are secrets**, and the adapter never returns any of them.

`getRedemption` now formats this as three lines: `Code: <pin>`, `PIN Code: <6 digits>` and `Valid until: YYYY-MM-DD`. Before, it was raw JSON. The adapter run against the real invoice confirmed the three line shapes. It also confirmed that `getOrderStatus` returns exactly `{status: "delivered", redemptionAvailable: true}`, that no access token, checkout URL or access link appears, and that only `get-invoice-by-id` was called.
